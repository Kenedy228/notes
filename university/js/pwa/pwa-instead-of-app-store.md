## 1. Зачем банку понадобилась PWA

[01:39–05:13](https://www.youtube.com/watch?v=778zEKLQIw4&t=99s)

После удаления аккаунта банка из App Store исчезли примерно полтора-два десятка
его приложений. Команде понадобился способ вернуть пользователям доступ
к продуктам без публикации в магазине Apple.

Обёртка над сайтом на основе WebView не решала основную проблему: такое
приложение всё равно требовалось распространять как нативное. Команда выбрала
**Progressive Web App (PWA)** — веб-приложение, которое браузер позволяет
использовать с интерфейсом, близким к установленному приложению.

Возможности, которые выделяет автор:

- Установка без аккаунта разработчика в магазине и без проверки релиза магазином.
- Иконка на домашнем экране и отдельный запуск приложения.
- Отображение без привычной адресной строки и элементов браузера.
- Работа без сети, если соответствующий сценарий реализован разработчиком.
- Push-уведомления на поддерживаемых платформах.

**Полностью заменить нативное приложение не удалось.** Поведение PWA различается
между платформами; особенно много ограничений команда встретила на iOS.

## 2. История технологии и различия платформ

[05:26–08:21](https://www.youtube.com/watch?v=778zEKLQIw4&t=326s)

Исторические ориентиры доклада:

| Период | Событие |
| --- | --- |
| 1999 | Microsoft HTML Applications (`.hta`) как ранний подход к приложениям на веб-технологиях |
| 2007 | Представление iPhone и ставка на веб-приложения до появления App Store |
| 2015 | Формулирование концепции PWA Фрэнсис Бэрримэн и Алексом Расселлом |
| 2016–2017 | Рост интереса к PWA, в том числе в регионах с дорогим или слабым интернетом |

Офлайн-работа и экономия трафика сделали подход полезным для пользователей
с ограниченным доступом к сети.

Ключевая мысль автора: единая технология не означает одинаковую реализацию.
Опыт разработки под Android нельзя автоматически переносить на iOS.

## 3. Три составляющие PWA

[08:21–09:26](https://www.youtube.com/watch?v=778zEKLQIw4&t=501s)

| Составляющая | За что отвечает |
| --- | --- |
| **Web App Manifest** | Представляет приложение браузеру: название, иконки, запуск и отображение |
| **HTTPS** | Обеспечивает защищённый контекст, необходимый для Service Worker |
| **Service Worker** | Обрабатывает сетевые события, обеспечивает работу с кэшем, офлайн-сценарии и push |

Эти элементы автор использует как базовую схему устройства PWA. Наличие
манифеста или иконки само по себе не реализует перечисленные возможности.

## 4. Manifest — паспорт приложения

[09:26–15:46](https://www.youtube.com/watch?v=778zEKLQIw4&t=566s)

Браузер узнаёт о манифесте из ссылки в HTML. Имя файла может быть произвольным;
важно явно его подключить:

```html
<link rel="manifest" href="/manifest.json">
```

Основные поля:

| Поле | Назначение и замечания из доклада |
| --- | --- |
| `name` | Полное название приложения, используемое в том числе при установке |
| `short_name` | Короткое название для ограниченного пространства интерфейса |
| `icons` | Иконки приложения разных размеров |
| `start_url` | Страница, с которой начинается запуск |
| `scope` | Область адресов приложения |
| `display` | Предпочтительный режим отображения |
| `theme_color` | Цвет темы, который браузер может использовать для своего интерфейса |
| `background_color` | Цвет фона при запуске, до отрисовки интерфейса |

Автор рекомендует задавать и полное, и короткое название, учитывая ограничения
места на устройстве. Конкретный выбор названия и его обрезку выполняет платформа.

### Иконки и настройки для iOS

В докладе для Android рассматривается набор иконок разных размеров, включая
192 × 192 и 512 × 512. Для iOS автор отдельно рекомендует `apple-touch-icon`
размером 180 × 180 и дополнительные настройки в HTML:

```html
<link rel="apple-touch-icon" href="/icons/apple-touch-icon.png">
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-title" content="My App">
```

Практическая рекомендация автора — PNG без прозрачности: в его опыте старые
версии ОС могли заливать прозрачную область чёрным. При отсутствии подходящей
иконки устройство может сформировать собственную, поэтому результат установки
нужно проверять на реальных устройствах.

## 5. Запуск, область приложения и режим отображения

[15:46–23:40](https://www.youtube.com/watch?v=778zEKLQIw4&t=946s)

**`start_url`** задаёт точку входа. **`scope`** определяет область навигации,
которая считается частью установленного приложения.

Например, при `start_url: "/app/"` и `scope: "/app/"`:

```plaintext
/app/             ← запуск
/app/payments     ← внутри области приложения
/app/profile      ← внутри области приложения
/external/        ← за пределами области
```

Выход за пределы области приложения может изменить режим отображения
или открыть браузер. В опыте команды на iOS обратная ссылка не возвращала
пользователя в установленную PWA.

Причина, которую подчёркивает автор, — **разделение контекстов браузерной
версии и установленной PWA**. Например, выбранная в PWA тёмная тема
не обязана появиться в браузере: локальные настройки не следует считать общими.
Поэтому команда старается удерживать основной сценарий внутри приложения.

Для `display` рассматриваются `browser`, `minimal-ui`, `standalone`
и `fullscreen`. Для интерфейса без обычных панелей браузера автор акцентирует
`standalone`; поддержку остальных вариантов нельзя считать одинаковой
на Android и iOS.

`background_color` и `theme_color` помогают согласовать запуск с оформлением
приложения. Это особенно заметно при тёмной теме: неподходящий фон во время
загрузки или обновления создаёт светлое мелькание.

## 6. Service Worker и его жизненный цикл

[23:40–29:57](https://www.youtube.com/watch?v=778zEKLQIw4&t=1420s)

> **Service Worker** — событийный скрипт, выполняющийся отдельно от страницы.
> Он может перехватывать запросы контролируемых страниц, выбирать источник
> ответа и обрабатывать push-события. Интерфейс отображает сама страница.

Пример регистрации, соответствующий рассматриваемой схеме:

```js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js', { scope: '/' })
    .catch(error => console.error('Ошибка регистрации SW:', error));
}
```

**Регистрация.** Браузеру передают адрес скрипта и область его действия.
Ошибки нужно обрабатывать; автор рекомендует предусматривать повторную попытку.
Логика кэширования появляется только после её реализации в самом воркере.

**Установка (`install`).** Подготавливают необходимые ресурсы: HTML, JS, CSS,
иконки. Автор предостерегает от преждевременного удаления рабочего кэша:
при неудачном обновлении без сетевого запасного пути пользователь может
получить белый экран.

**Ожидание (`waiting`).** Новая версия может быть установлена, пока страницы
продолжают использовать старую. Следует заранее продумать уведомление
об обновлении, перезагрузку и поведение открытых вкладок.

**Активация (`activate`).** Место для удаления устаревших кэшей и необходимых
миграций. Не следует задерживать активацию длительными операциями.

**Работа активного воркера.** Обработка запросов и других событий согласно
реализованной стратегии. Какая версия контролирует страницу, существенно
для согласованности интерфейса и ресурсов после обновления.

Главная практическая задача — спроектировать обновление так, чтобы одновременно
учесть старые вкладки, новую версию ресурсов и незавершённую работу пользователя.

## 7. Стратегии кэширования и пример брокерского приложения

[29:57–33:15](https://www.youtube.com/watch?v=778zEKLQIw4&t=1797s)

| Стратегия | Как работает | Для чего полезна |
| --- | --- | --- |
| **Cache-first** | Сначала кэш; если ответа нет — сеть | Быстрый доступ к ресурсам, для которых допустимо сохранённое содержимое |
| **Network-first** | Сначала сеть; при сбое возможен ответ из кэша | Данные, где приоритетна актуальность |
| **Stale-while-revalidate** | Сразу сохранённый ответ, параллельно обновление из сети | Быстрый показ с обновлением кэша для следующих обращений |
| **Offline fallback** | Если основной путь не дал ответа — подготовленная заглушка | Понятное сообщение о недоступности вместо пустого экрана |

Обновление кэша само по себе не обновляет уже отображённый экран: для этого
нужна отдельная логика страницы.

### Почему команда предпочла сеть

Начальный экран брокерского приложения показывает портфель пользователя.
Если сначала отобразить старое состояние без недавно купленных бумаг,
пользователь может решить, что активы исчезли.

Поэтому команда предпочитает **получить актуальные данные и показать загрузку**,
а затем отобразить портфель. Автор отмечает небольшой объём кэширования
и значимость обновлений через сокеты.

Вывод из кейса: минимальное время до появления экрана не всегда важнее
достоверности информации на этом экране.

## 8. Сбои, отладка и HTTPS

[33:15–35:07](https://www.youtube.com/watch?v=778zEKLQIw4&t=1995s)

Типичная проблема в опыте команды — «залипание» кэша и белый экран у части
пользователей. Исправление усложняется тем, что нужно доставить новую версию
воркера в приложение с уже проблемным состоянием.

Команда использует логи и дополнительные сценарии обработки сбоев.
Запасные ответы и экраны следует проектировать заранее, вместе с обновлением.

Service Worker требует защищённого контекста. Для обычного размещения
используется HTTPS; `localhost` допускается для локальной разработки.
Защита канала важна, поскольку подмена скрипта, управляющего запросами,
создаёт угрозу данным пользователя.

## 9. Установка, хранение, push и ссылки на iOS

[35:07–39:48](https://www.youtube.com/watch?v=778zEKLQIw4&t=2107s)

### Установка

Автор противопоставляет предложение установки на Android ручному сценарию
на iOS. Во втором случае продукту приходится давать пользователю инструкцию
по добавлению приложения на домашний экран.

При этом часть возможностей веб-приложения работает и в обычной вкладке:
не следует понимать установку как обязательное условие работы любого
Service Worker или любого офлайн-сценария.

### Хранение данных

По наблюдениям автора, после перерыва в использовании у части пользователей
пропадало локальное состояние. Он связывает это с механизмами очистки iOS
и упоминает Intelligent Tracking Prevention (ITP).

Практический вывод — предусмотреть повторную загрузку и восстановление
состояния. Названные в докладе сроки очистки нельзя использовать как гарантию
или таймер: причины очистки и правила ITP требуют отдельного уточнения.

### Push-уведомления

На iOS запрос разрешения связан с явным действием пользователя. Автор также
предупреждает об отзыве разрешения при использовании push для скрытых фоновых
операций без показа уведомлений.

Нельзя строить критический пользовательский сценарий на предположении,
что подписка на уведомления всегда существует и сохраняется бессрочно.

### Deep Links

**Deep Link** — ссылка, ведущая на конкретный экран приложения с нужными
параметрами. В рассматриваемом командой сценарии ссылка из SMS на iOS
открывала браузерную версию, а не установленную PWA.

Рабочий путь, который предлагает автор для такой навигации, —
**нажатие на push-уведомление с последующим открытием нужного экрана**.
Внешние ссылки и переходы из уведомлений нужно проверять отдельно.

### Web Share

Автор разделяет два сценария:

| Действие | Android в опыте автора | iOS в опыте автора |
| --- | --- | --- |
| Отправить данные из PWA через системное меню | Поддерживается | Поддерживается |
| Выбрать PWA получателем данных, Share Target | Поддерживается | Не поддерживается |

Например, отправка ссылки в мессенджер не означает, что получатель сможет
открыть её непосредственно в установленной PWA.

## 10. Результат перехода и ответы на вопросы

[40:27–43:57](https://www.youtube.com/watch?v=778zEKLQIw4&t=2427s)

**Как изменился опыт разработчиков?** Команда была преимущественно нативной;
не все знали JavaScript. Пришлось быстро переучиваться и разбираться
в поведении браузера, кэша и Service Worker. Приложение сделали на React,
однако подробного сравнения с альтернативными фреймворками в записи нет.

**Какой функциональный результат?** По оценке автора, удалось закрыть около
**80% функциональности** нативного приложения и выполнить необходимое заказчику.
Это оценка конкретного проекта, а не универсальный показатель возможностей PWA.

**Отказались ли от нативных приложений?** Нет, соответствующие команды
продолжили работу. При восстановлении устойчивого доступа к App Store автор
предпочёл бы нативный вариант; особенно критично он оценивает ограничения iOS.

**Используют ли PWA на Android?** Да, несмотря на возможность установить APK.
Команда учитывает обе мобильные платформы и расширяет поддержку на десктоп.

**Какие преимущества остаются у PWA?** Независимая от магазина доставка
и быстрые обновления: исправление можно развернуть без ожидания проверки
новой версии магазином. По мнению автора, эти преимущества в его кейсе
не перевешивают все достоинства нативного опыта.

> Итог доклада: PWA помогла сохранить доступ к продукту после удаления из
> App Store, но стала компромиссом. Возможность замены нативного приложения
> определяется конкретными сценариями, требованиями к данным и ограничениями ОС.

## Технические уточнения к словам докладчика

Это пояснения составителя, отделённые от пересказа записи.

1. **Service Worker не обязательно один на весь сайт.** Возможны регистрации
   с разными областями действия. У регистрации есть устанавливаемая, ожидающая
   и активная версии; новый скрипт для той же области может обновить регистрацию.
   Поэтому фразу автора «первый зарегистрировался, остальные игнорируются»
   нельзя использовать как общее правило. Воркер также не получает обычные
   нажатия кнопок автоматически: это события страницы.
   [Спецификация Service Workers](https://www.w3.org/TR/service-workers/#service-worker-registration-concept).

2. **Активация не означает автоматическую перезагрузку страницы.** Обновление
   воркера, получение контроля над страницей и её перезагрузка — разные действия.
   Нужное поведение следует реализовать явно.
   [Управление клиентами Service Worker](https://www.w3.org/TR/service-workers/#control-and-use).

3. **Web Push на iOS появился в 16.4.** В записи около 21:45 звучит 2018 год,
   но WebKit указывает поддержку для приложений на домашнем экране начиная
   с iOS/iPadOS 16.4 и запрос разрешения после действия пользователя.
   [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/).

4. **Очистку установленной PWA нельзя автоматически объяснять семидневным
   лимитом ITP.** WebKit отдельно исключает собственный домен приложения
   на домашнем экране из этого лимита и указывает на изоляцию его данных
   от Safari. Наблюдение о потере данных полезно учитывать, но конкретную
   причину нужно устанавливать отдельно.
   [WebKit: Tracking Prevention](https://webkit.org/tracking-prevention/).

Автоматические субтитры имеют два предупреждения `TIMESTAMP_OUT_OF_RANGE`
в последних сегментах: их окончание выходит за длительность из метаданных
примерно на 1,2 секунды. Таймкоды разделов служат навигацией по записи.
