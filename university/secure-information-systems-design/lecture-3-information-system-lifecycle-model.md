# Модели жизненного цикла информационных систем

Выделяют три основные модели:

```plaintext
МОДЕЛИ ЖИЗНЕННОГО ЦИКЛА
│
├── Каскадная
├── Инкрементная
└── Спиральная
```

## Каскадная модель

*Псевдонимы*: однократный проход, водопадная модель, классическая модель.

```plaintext
Формирование требований
        ↓
Анализ требований
        ↓
Проектирование
        ↓
Кодирование
        ↓
Тестирование
        ↓
Внедрение
        ↓
Итоговый продукт
        ↓
Сопровождение и эксплуатация
```

Идея каскадной модели заключается в том, что **стадии выполняются
последовательно, одна за другой**.

```plaintext
[Требования]
     │
     ▼
  закончили
     │
     ▼
[Проектирование]
     │
     ▼
  закончили
     │
     ▼
[Реализация]
     │
     ▼
    ...
```

На каждой стадии формируется **законченный набор результатов, отвечающий
критериям полноты и согласованности: документация, ПО, аппаратное обеспечение и
т.д.**

```plaintext
Требования
    ↓
[готовый результат стадии]
    ↓
Проектирование
    ↓
[готовый результат стадии]
    ↓
Реализация
    ↓
[готовый результат стадии]
```

Поскольку стадии идут в понятной последовательности, то становится легче
планировать сроки выполнения, деньги, материальные ресурсы, людей для каждого этапа.

```plaintext
Требования       → 1 месяц
Проектирование   → 2 месяца
Разработка       → 4 месяца
Тестирование     → 1 месяц
Внедрение        → 1 месяц
```

Поэтому главное достоинство модели можно свести к **предсказуемости** и **удобству планирования**.

К **недостатку** модели относится следующее: в начале проекта требования заказчика
определены лишь частично, а результаты разработки заказчик получает только в
конце. Если требования были изложены неточно или изменились за время разработки,
итоговая ИС может не удовлетворять его потребностям.

```plaintext
Требования  ← ❌ неправильно поняли заказчика, ошибка протащится через весь проект
    ↓
Анализ
    ↓
Проектирование
    ↓
Код
    ↓
Тестирование
    ↓
Внедрение
```

Каскадная модель лучше соответствует **типовым проектам**, где технология и
методы решения задачи хорошо проработаны. Также предполагается достаточная
обеспеченность ресурсами для реализации проекта в относительно сжатые сроки.

## Инкрементная модель

Идея инкрементной модели заключается в том, чтобы **не создавать всю систему за
один проход, а вводить ее частями - отдельными очередями (версиями).**

Условно заказчику нужна система:

```plaintext
Итоговая ИС
│
├── Личный кабинет
├── Расписание
├── Успеваемость
├── Электронные заявления
└── Уведомления
```

При каскадной модели мы стремимся пройти ЖЦ **для всего продукта:**

```plaintext
Требования
    ↓
Анализ
    ↓
Проектирование всей системы
    ↓
Реализация всей системы
    ↓
Тестирование
    ↓
Внедрение
    ↓
Итоговый продукт
```

При инкрементной модели:

```plaintext
Итоговая система
       ▲
       │
 ┌─────┴─────┐
 │ 3 очередь │  + новая часть
 └─────▲─────┘
       │
 ┌─────┴─────┐
 │ 2 очередь │  + новая часть
 └─────▲─────┘
       │
 ┌─────┴─────┐
 │ 1 очередь │  первая версия
 └───────────┘
```

Каждая очередь увеличивает возможности системы.

### Как устроена очередь

Для первой очереди показана следующая последовательность выполнения этапов ЖЦ:

```plaintext
Формирование требований
        ↓
Анализ требований
        ↓
Проектирование
        ↓
Кодирование
        ↓
Тестирование
        ↓
Внедрение
        ↓
1 очередь (версия)
        ↓
Сопровождение и эксплуатация
```

После этого создается следующая версия, затем следующая и т.д.

То есть можно сказать, что **инкрементная модель содержит несколько
последовательных поставок продукта.**

Причем уже первая версия может эксплуатироваться, пока развивается следующая.

```plaintext
Версия 1
├── эксплуатация ──────────────────────►
│
└────────────► Версия 2
               ├── эксплуатация ──────►
               │
               └────────────► Версия 3
```

Применение инкрементной модели характерно **для сложных систем, для которых
имеется четкое видение конечного результат и у заказчика, и у разработчика.** Мы
примерно знаем, какой должна стать конечная система:

```plaintext
                   КОНЕЧНАЯ ИС
                       ▲
                       │
              понимаем заранее
                       │
          ┌────────────┴────────────┐
          │                         │
      Заказчик                 Разработчик
```

Но не можем или не хотим реализовывать все сразу.

#### Основные причины, почему система может разбиваться на версии:

1. не хватает денег заказчика

Проект дорогой, и заказчик не может профинансировать его целиком сразу, например:

```plaintext
Вся система = 30 млн

2026 → версия 1 → 10 млн
2027 → версия 2 → 10 млн
2028 → версия 3 → 10 млн
```

2. не хватает ресурсов разработчиков

Например, конечная система большая:

```plaintext
Нужно реализовать:

├── A
├── B
├── C
├── D
├── E
├── F
└── G
```

Но команда физически не может сделать все за требуемый срок. Тогда:

```plaintext
Версия 1 → A + B
Версия 2 → C + D
Версия 3 → E + F + G
```

3. нужно поэтапно внедрять систему

Пользователям тоже может быть тяжело сразу перейти на огромную новую систему. Поэтому:

```plaintext
Сначала:
Расписание

        ↓ пользователи освоили

Потом:
Расписание + успеваемость

        ↓ освоили

Потом:
+ заявления
+ уведомления
```

Достоинства и недостатки инкрементальной модели в целом такие же, как у
каскадной модели, но **заказчик раньше видит результат.** И после первой версии
заказчик уже может оценить результат.

То есть инкрементность в данной модели достигается за счет **постепенного
наращивания продукта.**

## Спиральная модель

Главная идея спиральной модели заключается в том, что **система развивается
итерациями, и на каждой итерации мы уточняем цели и требования, анализируем
риски, разрабатываем очередную версию и планируем следующий виток**.

Один виток спирали состоит из четырех частей:

```plaintext
1. Определение целей,
   альтернатив и ограничений
   (формирование требований)
             ↓
2. Оценка альтернатив,
   выявление и устранение рисков
   (анализ требований)
             ↓
3. Разработка и верификация
   (проектирование, кодирование,
   интеграция, тестирование,
   внедрение)
             ↓
4. Планирование следующей фазы
   (сопровождение и эксплуатация)
             ↓
       СЛЕДУЮЩИЙ ВИТОК
```

Так появляются первая, вторая, третья и последующие версии.

В данной модели мы возвращаемся к похожим процессам снова и снова, но каждый раз
система становится более развитой:

```plaintext
          ┌──→ Версия 1
          │
     ┌────┘
     │    ┌────→ Версия 2
     │    │
     └────┴────────→ Версия 3
```

Инкрементная и спиральная модели **разрабатывают систему версиями.**

```plaintext
Инкрементная:

Версия 1 → Версия 2 → Версия 3


Спиральная:

Версия 1 → Версия 2 → Версия 3
```

Но разные предпосылки. Для инкрементной модели мы знаем что должно получиться в
итоге, но идем частями:

```plaintext
Конечный ЛК
│
├── Расписание
├── Оценки
├── Заявления
└── Уведомления

V1 → Расписание
V2 → + Оценки
V3 → + Заявления
V4 → + Уведомления
```

Основные требования определены в начале, а изменения требований по мере
прохождения этапов ЖЦ незначительны.

В спиральной модели **мы не обязаны заранее достаточно хорошо представлять
конечную систему.**

```plaintext
Начальные представления
        ↓
     Версия 1
        ↓
получили результат,
уточнили требования,
оценили риски
        ↓
     Версия 2
        ↓
снова анализ
        ↓
     Версия 3
        ↓
       ...
```

`Поэтому требования могут существенно развиваться вместе с продуктом. Заказчик быстрее
получает работоспособный продукт. Но для команды при каждом прохождении витка спирали
может вырисовываться совершенно новая система.`

Главный недостаток спиральной модели - мы не знаем, сколько займет весь проект
времени и сколько ресурсов потребуется в итоге.

## Модификация программного обеспечения

Выделяют четыре уровня изменений:

```plaintext
Ревизия
   ↓
Модификация
   ↓
Версия
   ↓
Развитие (очередь)
```

### Ревизия

**Ревизия** - это оперативные изменения ПО, информационного обеспечения или БД,
которые **необязательны в данный момент к передаче на объекты внедрения** и связаны
с устранением ошибок или усовершенствованием.

Ключевой признак ревизии: **изменение сделали, но прямо сейчас не обязаны
распространять его пользователям или на объекты внедрения.**

Например:

```plaintext
Работает версия системы
        │
        ▼
Нашли небольшой баг
        │
        ▼
Исправили
        │
        ▼
Но срочно раскатывать исправление
на все объекты не требуется
        │
        ▼
РЕВИЗИЯ
```

### Модификация

**Модификация** - это оперативные изменения ПО, информационного обеспечения или БД,
которые **обязательны в данный момент к передаче на объекты внедрения** и связаны
с устранением ошибок или усовершенствованием.

При этом изменения:

- могут изменять эксплуатационные характеристики;
- не изменяют функции, предусмотренные ТЗ;
- могут быть связаны с исправлением ошибок и усовершенствованием.

```plaintext
РЕВИЗИЯ
→ передавать сейчас необязательно

МОДИФИКАЦИЯ
→ передавать обязательно
→ функции по ТЗ при этом не меняются
```

### Версия

**Версия** - это изменения ПО, информационного обеспечения или БД, обязательные
для передачи на объекты внедрения и позволяющие:

- выполнять заявленные или дополнительные функции;
- либо перейти на новые операционные системы;
- либо перейти на новую информационную среду.

Например:

```plaintext
Версия 1

ЛК
├── расписание
└── оценки


Версия 2

ЛК
├── расписание
├── оценки
└── уведомления  ← новая функция
```

### Развитие (очередь)

**Развитие (очередь)** - это плановые изменения ИС, связанные с введением новых
функций, улучшением эксплуатационных характеристик, переходом на новую
информационную среду, внедрением новых комплексов технических средств, новых
информационных технологий и т.д.

Например:

```plaintext
                   ЛК ДВГУПС
                       │
               существующая ИС
                       │
                       ▼
              РАЗВИТИЕ / ОЧЕРЕДЬ
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     новые функции   новая       новые технические
                    технология       средства
```

То есть это уже не просто оперативное изменение отдельного ПО, а **плановое
изменение (расширение) ИС.**
