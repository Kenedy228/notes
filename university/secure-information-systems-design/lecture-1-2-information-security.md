# Информационная безопасность

## Объект защиты

Если ИС работает с информацией, то возникает необходимость защищать не только
саму программу. **Объектами, требующими защиту**, могут быть:

```plaintext
                ИНФОРМАЦИОННАЯ СИСТЕМА
                          │
       ┌──────────────────┼──────────────────┐
       ▼                  ▼                  ▼
    Информация       Компоненты          Каналы связи
       │                  │                  │
       │                  ├── ПО             └── сеть
       │                  ├── серверы
       │                  └── хранилища
       │
       └── персональные данные
           учетные данные
           документы
           служебная информация
           и т.д.
```

Например, если злоумышленник не получил доступ к базе данных, но смог
перехватить информацию **во время ее передачи**, задача защиты все равно не
выполнена. Аналогично, идеально защищенное сетевое соединение не поможет, если
пользователь системы имеет избыточные права и может прочитать данные, которые
ему не предназначены.

Поэтому защищенную ИС нельзя рассматривать только как:

```plaintext
обычная ИС
    +
антивирус
```

Гораздо правильнее мыслить так:

```plaintext
Проектируем ИС
      │
      ├── определяем данные
      ├── определяем компоненты
      ├── определяем пользователей
      ├── определяем связи
      ├── определяем границы
      └── определяем информационные потоки
                    │
                    ▼
          понимаем, ЧТО и ГДЕ
              необходимо защищать
```

## Защита информации

ИС хранит, обрабатывает и передает информацию. При этом необходимо не только
обеспечить возможность работы с этой информацией, но еще и ее **защиту**.

> В самом общем виде **защита информации** нужна для того, чтобы информация
> сохраняла необходимые свойства даже при возникновении ошибок, сбоев или
> преднамеренных действий.

Например, ИС университета содержит сведения о студентах:

```plaintext
Студент
│
├── ФИО
├── дата рождения
├── оценки
├── сведения о зачислении
└── документы
```

Можно представить несколько различных проблем:

```plaintext
Злоумышленник получил список студентов
                ↓
       нарушение конфиденциальности


Кто-то изменил оценку 3 → 5
                ↓
         нарушение целостности


Система недоступна во время экзамена
                ↓
         нарушение доступности
```

Обратим внимание, что во всех трех случаях проблема связана с одной ИС, но
характер нарушения совершенно разный. Отсюда появляются три фундаментальных
свойства информационной безопасности:

```plaintext
                 ИНФОРМАЦИЯ
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
Конфиденциальность Целостность Доступность
```

Эту модель обычно называют:

```plaintext
C — Confidentiality — конфиденциальность
I — Integrity       — целостность
A — Availability    — доступность
```

### Конфиденциальность

> **Конфиденциальность** означает, что информация не должна быть доступна лицам,
> которым доступ к ней не разрешен.

Пример:

```plaintext
                  Оценки студента
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Студент      Преподаватель  Посторонний
          │             │             │
       доступ         доступ       НЕТ доступа
```

Если посторонний пользователь смог получить оценки студента, информация при этом
необязательно была изменена или уничтожена. Она просто стала известна тому, кому
не должна была быть доступна.

```plaintext
Было:

Данные ──→ только разрешённые пользователи


Стало:

Данные ──→ разрешённые пользователи
   │
   └─────→ посторонний

                ↓

Нарушение конфиденциальности
```

Причем конфиденциальность относится не только к чтению записей из базы данных.
Информация может быть раскрыта:

```plaintext
при хранении
    ↓
утечка БД

при передаче
    ↓
перехват трафика

при обработке
    ↓
доступ к памяти / логам

при отображении
    ↓
пользователь увидел чужие данные

при резервном копировании
    ↓
утечка backup
```

> Поэтому защищается не просто файл или таблица, а информация **на различных этапах
> ее существования в системе**.

### Целостность

> **Целостность** означает сохранение правильности и непротиворечивости
> информации и недопущение ее несанкционированного изменения или уничтожения.

Например:

```plaintext
БД

student_id | grade
-----------+------
42         | 3
```

Если кто-либо без соответствующих полномочий изменил:

```plaintext
3 → 5
```

Конфиденциальность при этом может вообще не пострадать. Проблема заключается в другом:

```plaintext
правильные данные
│
│ неразрешённое изменение
▼
изменённые данные

      ↓

нарушение целостности
```

Но целостность — это не только защита от злоумышленника.

Представим перевод денег:

```plaintext
Счёт A Счёт B
1000 ₽ 500 ₽

     перевод 100 ₽
          │
          ▼

Счёт A Счёт B
900 ₽ 600 ₽
```

Если из-за ошибки произошло:

```plaintext
Счёт A Счёт B
900 ₽ 500 ₽
```

Данные тоже потеряли целостность, хотя никакого злоумышленника не было.

Следовательно, причиной нарушения целостности могут быть:

```plaintext
Нарушение целостности
│
├── действия злоумышленника
├── ошибка пользователя
├── ошибка программы
├── сбой оборудования
└── ошибка при передаче данных
```

> Это важная мысль: **информационная безопасность занимается не исключительно хакерами**.

### Доступность

> **Доступность** означает возможность получить доступ к информации или
> необходимой функции системы тогда, когда это требуется авторизованному пользователю.

Например, студент имеет право открыть LMS:

```plaintext
Студент
   │
   │ GET /courses
   ▼
  LMS
   │
   ▼
Курсы
```

Но сервер перестал отвечать:

```plaintext
Студент
   │
   │ GET /courses
   ▼
  LMS
   X
   X
   X
```

Никто не прочитал секретные данные. Никто их не изменил. Но воспользоваться системой невозможно.

```plaintext
Конфиденциальность ✓
Целостность        ✓
Доступность        ✗
```

Причины нарушения доступности тоже могут быть совершенно различными:

```plaintext
Недоступность
     │
     ├── отказ оборудования
     ├── ошибка ПО
     ├── потеря сетевого соединения
     ├── перегрузка
     ├── неправильная конфигурация
     └── преднамеренная атака
```

Например, DoS/DDoS является уже преднамеренной попыткой нарушить доступность системы.

### CIA вместе

> Самое важное — **не воспринимать эти свойства независимо друг от друга**.

Возьмём базу данных:

```plaintext
                   База данных
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
Конфиденциальность  Целостность    Доступность
        │               │               │
   кто может        кто может       можем ли мы
    читать?          изменять?      получить доступ?
```

Например:

```plaintext
БД полностью закрыта от всех пользователей.

Конфиденциальность: очень высокая
Доступность:        отсутствует
```

Такая система практически бесполезна. И наоборот:

```plaintext
БД доступна всему Интернету без авторизации.

Доступность:        высокая
Конфиденциальность: отсутствует
```

Поэтому задача заключается не в максимизации одного свойства, а в обеспечении
необходимого уровня каждого свойства в соответствии с назначением системы.

## Активы ИС

Теперь возникает вопрос: **что именно мы защищаем?**

Для этого удобно использовать понятие актива.

> В контексте информационной безопасности **активом** можно считать то, что представляет
> ценность для организации или системы и поэтому требует защиты.

Самый очевидный актив — информация:

```plaintext
Информационные активы
│
├── персональные данные
├── учетные данные
├── документы
├── финансовая информация
├── результаты обучения
└── служебная информация
```

Но защищать приходится не только сами данные. Например:

```plaintext
                    АКТИВЫ ИС
                        │
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
   Информация          ПО          Инфраструктура
       │                │                │
   документы         backend           серверы
   аккаунты          frontend          сеть
   записи БД         сервисы           хранилища
```

Кроме того, ценность могут представлять:

```plaintext
├── учётные записи;
├── криптографические ключи;
├── конфигурация;
├── резервные копии;
├── журналы событий;
└── сами функции системы.
```

Последний пункт интересен. Например, функция:

```plaintext
POST /payments
```

Сама является ценным ресурсом. Даже если злоумышленник не получил никаких данных,
возможность несанкционированно выполнить эту операцию уже является серьёзной проблемой.

## Угроза

После определения активов возникает следующий вопрос: **что плохого может с ними произойти?**

Здесь появляется понятие угрозы.

> **Угроза** — потенциальная возможность нарушения безопасности актива.

Например, имеется:

```plaintext
Актив:
База персональных данных студентов
```

Для неё возможны различные угрозы:

```plaintext
                 База данных
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   раскрытие       изменение      уничтожение
       │              │              │
       ▼              ▼              ▼
конфиденциальность целостность   доступность
```

Именно здесь CIA становится практически полезной моделью. Мы можем взять актив и спросить:

```plaintext
АКТИВ: база студентов

C:
Может ли информацию получить посторонний?

I:
Может ли кто-либо неправомерно изменить информацию?

A:
Может ли информация стать недоступной?
```

## Нарушитель

Но угроза сама по себе ещё не объясняет, кто или что может её реализовать.

Если речь идёт о преднамеренных действиях, появляется понятие **нарушителя**.

> **Нарушитель** — субъект, действия которого могут привести к нарушению безопасности
> информационной системы.

При слове «нарушитель» легко сразу представить хакера из Интернета. Но это слишком
узкое представление. Нарушитель может находиться как снаружи, так и внутри организации:

```plaintext
                    НАРУШИТЕЛЬ
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
           внешний               внутренний
              │                     │
         Интернет                сотрудник
         стороннее лицо          администратор
                                 пользователь
```

Например, сотрудник организации уже может иметь:

```plaintext
логин
пароль
доступ к сети
доступ к части системы
```

Поэтому его возможности принципиально отличаются от возможностей случайного человека из Интернета.

> Но не всякая проблема связана с нарушителем.

Здесь важно не смешивать два случая:

```plaintext
                  Нарушение безопасности
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
       преднамеренное              непреднамеренное
             │                           │
        нарушитель                   ошибка
        атака                        отказ
                                     сбой
```

Например:

```plaintext
Злоумышленник удалил БД
        ↓
преднамеренное нарушение


Диск вышел из строя
        ↓
непреднамеренное нарушение
```

Результат может оказаться одинаковым: БД недоступна, но причины совершенно разные.
Поэтому защищённая система **должна учитывать не только атаки, но и ошибки, отказы и сбои**.

## Уязвимость

Мы уже определили угрозу как потенциальную возможность нарушения безопасности актива.
Но само существование угрозы ещё не означает, что она может быть успешно реализована.
Для реализации угрозы обычно необходимо наличие некоторой слабости системы.

> **Уязвимость** — недостаток или слабое место информационной системы, которое может
> быть использовано для нарушения её безопасности.

Рассмотрим простой пример. Есть информационная система:

```plaintext
Интернет
│
▼
Web-приложение
│
▼
БД
```

В базе данных находятся персональные данные.

```plaintext
Актив
↓
Персональные данные

Угроза
↓
Несанкционированное получение данных
```

Но каким образом посторонний пользователь сможет получить эти данные? Допустим, endpoint:

```plaintext
GET /users/42
```

Возвращает информацию о пользователе, но сервер не проверяет, имеет ли текущий пользователь
право просматривать пользователя 42.

Получается:

```plaintext
Пользователь
│
│ GET /users/42
▼
Backend
│
│ нет проверки прав
▼
БД
│
▼
чужие данные
```

Отсутствие необходимой проверки авторизации — **уязвимость**. Угроза существовала и раньше:

```plaintext
получение чужих данных
```

Но именно уязвимость создаёт возможность её реализации.

```plaintext
УГРОЗА
"чужие данные могут быть получены"
│
│ реализуется через
▼
УЯЗВИМОСТЬ
"сервер не проверяет право доступа"
```

Уязвимость не обязательно является ошибкой в исходном коде. Она может находиться
практически на любом уровне системы:

```plaintext
                    УЯЗВИМОСТИ
                         │
       ┌─────────────────┼──────────────────┐
       ▼                 ▼                  ▼
      ПО             Конфигурация         Процессы
       │                 │                  │
ошибка проверки     открытый порт      нет процедуры
прав доступа        слабые настройки   отзыва доступа

       ┌─────────────────┼──────────────────┐
       ▼                 ▼
 Инфраструктура        Персонал
       │                 │
устаревшая ОС        слабый пароль
нет резервирования   ошибки пользователя
```

Например:

```plaintext
уязвимость ПО
↓
неправильная проверка входных данных


уязвимость конфигурации
↓
БД доступна из Интернета


уязвимость процесса
↓
аккаунт уволенного сотрудника не блокируется


уязвимость инфраструктуры
↓
используется неподдерживаемая версия ОС


человеческий фактор
↓
сотрудник использует простой пароль
```

> Поэтому безопасность нельзя обеспечить только поиском багов в коде.

Угроза и уязвимость не одно и то же.

> **Угроза** отвечает на вопрос: что потенциально может произойти?
> **Уязвимость**: какая слабость позволяет этому произойти?

Например:

```plaintext
УГРОЗА
Несанкционированное изменение оценки
            │
            │ возможно из-за
            ▼
УЯЗВИМОСТИ
Отсутствует проверка роли пользователя
```

Или:

```plaintext
УГРОЗА
Раскрытие паролей пользователей
            │
            │ возможно из-за
            ▼
УЯЗВИМОСТИ
Пароли хранятся в открытом виде
```

Или:

```plaintext
УГРОЗА
Потеря доступности данных
            │
            │ последствия увеличиваются из-за
            ▼
УЯЗВИМОСТИ
Отсутствуют резервные копии
```

> Последний пример показывает важный момент: уязвимость необязательно непосредственно
> позволяет кому-то совершить атаку. Слабость системы также может делать последствия
> сбоя или другого события значительно серьёзнее.
