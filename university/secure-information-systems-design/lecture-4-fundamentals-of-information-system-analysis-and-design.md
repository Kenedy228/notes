# Основы анализа и проектирования информационных систем

## Особенности проектирования крупных ИС

Для крупных ИС характерно сразу несколько проблем.

### Сложность самой системы

В крупной ИС много:

- функций;
- процессов;
- данных;
- компонентов;
- связей между ними.

Причем проблема не только в количестве элементов, но и в сложности взаимосвязей.

```plaintext
                Университетская ИС
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Расписание      Контингент     Успеваемость
        │              │              │
        └──────┐   ┌───┘       ┌──────┘
               ▼   ▼           ▼
                  ЛК студента
                       │
                       ▼
                  Отчётность
```

Изменение одной части может затронуть несколько других частей. Поэтому
необходимо тщательно смоделировать и провести анализ данных и процессов.

### Подсистемы

В крупной ИС обычно существуют тесно взаимодействующие **компоненты (подсистемы).**

То есть вместо огромной программы мы рассматриваем

```plaintext
                  ИС
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
Подсистема A  Подсистема B  Подсистема C
      │            │            │
      └────────────┼────────────┘
                   │
            взаимодействие
```

### Отсутствие готового решения

Отсутствие прямых аналогов ограничивает возможность использования типовых
проектных решений и прикладных систем.

Допустим, мы делаем типовой интернет-магазин. Для многих задач уже понятно:

```plaintext
товар
корзина
заказ
оплата
доставка
```

Есть куча существующих решений и накопленного опыта. Но если разрабатывается
какая-нибудь специфичная железнодорожная ИС:

```plaintext
уникальная предметная область
            +
специфические процессы
            +
специфические требования
```

То готового решения может не существовать. Тогда приходится больше
**анализировать и проектировать самостоятельно.**

### Интеграция старого и нового

Практически никогда организация не говорит "удаляем вообще все старое и пишем ИС
заново". Обычно:

```plaintext
Существующая система A ───┐
                          │
Существующая система B ───┼── Новая ИС
                          │
Новая подсистема C ───────┘
```

И появляются вопросы:

```plaintext
Как обмениваться данными?

Какие форматы использовать?

Кто является источником истины?

Что делать при недоступности старой системы?

Как синхронизировать данные?
```

### Неоднородная среда

Крупная ИС может работать на разных аппаратных платформах в неоднородной среде.

Условно:

```plaintext
Windows workstation ─┐
Linux server ─────────┤
Legacy system ────────┼── ИС
Database server ──────┤
Другие платформы ─────┘
```

Поэтому при проектировании нельзя всегда исходить из того, что "у нас все
работает на моей машине".

### Разные команды разработчиков

Группы разработчиков могут различаться по квалификации и сложившимся традициям
использования инструментов.

Например:

```plaintext
Команда A
→ Java
→ свои практики

Команда B
→ C#
→ другие практики

Команда C
→ legacy
→ третьи практики
```

Но все это должно превратиться **в одну согласованную систему.**

### Большая продолжительность проекта

Крупная ИС может разрабатываться долго по причинам:

```plaintext
ограниченные возможности
команды разработчиков

        +

масштаб организации
и разная готовность подразделений
к внедрению
```

Например, систему сделали для огромной организации:

```plaintext
Подразделение A → готово внедрять

Подразделение B → персонал ещё не обучен

Подразделение C → старая инфраструктура

Подразделение D → ещё не подготовило данные
```

Поэтому внедрение тоже может растягиваться.

### Изменение требований

Потребности пользователей могут изменяться или уточняться в процессе создания **и
даже функционирования ИС.**

То есть:

```plaintext
Начало проекта

«Нам нужно X»
      ↓
разработка
      ↓
«Оказывается, X должен
работать немного иначе»
      ↓
эксплуатация
      ↓
«Теперь нам ещё нужен Y»
```

## Техническая документация

**Техническая документация** - это комплект графических, расчетных и текстовых
материалов, используемых на стадиях ЖЦ при создании, развитии и сопровождении ИС.

То есть документация сопровождает систему на протяжении ЖЦ:

```plaintext
Требования → Проектирование → Реализация → Внедрение → Эксплуатация
    │              │              │             │
    └──────────────┴──────────────┴─────────────┘
                  документация
```

Документация делится на три вида:

```plaintext
                Техническая документация
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Исходная       Проектная       Рабочая
                                  (эксплуатационная)
```

### Исходная документация

**Исходная документация** является основанием для выполнения работа по созданию,
развитию и сопровождению ИС.

То есть она отвечает примерно на вопрос: что необходимо сделать?

Главный пример - **техническое задание**.

### Проектная документация

**Проектная документация** определяет функциональные, архитектурные и
технические решения проектируемой ИС.

Один из проектных документов - **описание информационной технологии**. В нее входят:

- назначение;
- основные компоненты;
- сообщения;
- подготовку, формирование и передачу информации;
- основные БД;
- функции системы;
- взаимодействие со смежными системами;
- взаимодействие компонентов;
- технические средства;
- программные средства.

То есть концептуально:

```plaintext
ТЗ
│
├── система должна делать X
├── система должна делать Y
└── система должна удовлетворять Z


Описание информационной технологии
│
├── вот компоненты системы
├── вот основные БД
├── вот как передаётся информация
├── вот как компоненты взаимодействуют
├── вот технические средства
└── вот программные средства
```

Другим примером служит **проектное решение**. Он дополняет техническое или
частное техническое задание при модификации системы.

### Рабочая документация

**Рабочая документация** описывает уже фактическую реализацию этих решений и
содержит сведения, необходимые для ввода системы в действие, эксплуатации и
поддержания ее эксплуатационных характеристик.

```plaintext
ПРОЕКТНАЯ ДОКУМЕНТАЦИЯ

«Как систему РЕШИЛИ сделать?»

             ↓
          реализация
             ↓

РАБОЧАЯ ДОКУМЕНТАЦИЯ

«Как система ФАКТИЧЕСКИ реализована
и как с ней работать?»
```

В рабочую документацию входят: описание комплекса программ, эксплуатационные
руководства, программы методик и испытаний и другие.

## Проектирование

**Проектирование** - это процесс перехода от первичного описания системы в виде
технического задания к ее описанию в виде набора стандартных документов
(проектной документации), достаточных для создания системы.

Всего выделяют 11 принципов проектирования:

- декомпозиция;
- иерархическое упорядочение;
- концептуальная общность;
- абстрагирование;
- формализация;
- унификация;
- логическая независимость;
- многомодельность;
- непротиворечивость;
- информационная закрытость (инкапсуляция);
- полиморфизм.

### Декомпозиция

Рассматриваем сложную систему через более мелкие части:

```plaintext
                 ИС
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
 Подсистема A  Подсистема B  Подсистема C
       │
    ┌──┴──┐
    ▼     ▼
   A1     A2
```

Вместо того, чтобы пытаться спроектировать весь ЛК ДВГУПС, можно работать с
отдельными подсистемами, функциями и задачами.

### Иерархическое упорядочение

Полученные из декомпозиции элементы организуются по уровням:

```plaintext
Система
   │
   ├── Подсистема
   │      │
   │      ├── Компонент
   │      └── Компонент
   │
   └── Подсистема
          │
          └── Компонент
```

### Абстрагирование

При рассмотрении объекта можно концентрироваться на существенных для текущей
задачи свойствах и не тащить сразу все детали.

Условно сначала:

```plaintext
Система обучения

Student ─── Enrollment ─── Course
```

Нас пока может не интересовать:

```plaintext
какой SQL-тип у student_id
какой индекс в PostgreSQL
как называется Go-структура
какой HTTP endpoint используется
```

Мы рассматриваем систему на более высоком уровне, а детали уточнить позже.

### Формализация

Вместо произвольного "студент записывается на курс, потом у него есть попытки
теста и все такое..." используем определенные форма представления модели:

```plaintext
Student
   │
Enrollment
   │
Course
```

### Унификация

Стремление использовать единообразные решения и способы представления вместо
множества произвольных вариантов.

### Многомодельность

Одной модели недостаточно, чтобы полноценно описать сложную ИС. Например:

```plaintext
                    ИС
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   Модель данных   Модель       Модель
                   поведения    компонентов
```

Потому что одна диаграмма может хорошо показать структуру данных, но плохо
показать поведение системы. Другая хорошо показывает процессы, но ничего не
говорит о физической архитектуре. Поэтому систему приходится описывать
несколькими моделями с разных точек зрения.

### Непротиворечивость (согласованность)

Модели одной системы не должны противоречить друг другу. Например:

```plaintext
Модель A говорит:
Student связан с Course

Модель B говорит:
Student вообще не имеет отношения к Course
```

Такая ситуация не должна появиться при моделировании.

### Инксапсуляция и полиморфизм

Присуще объектно-ориентированному проектированию и повторяют концепции из
объектно-ориентированного программирования.

## Модели информационных систем

**Модель** - это совокупность взаимосвязанных абстрактных элементов с возможным
указанием их свойств, поведения и связей между ними. Модель не является
системой, а лишь некоторым ее представлением.

### Классификация моделей

Модели классифицируются по нескольким независимым признакам:

```plaintext
КЛАССИФИКАЦИЯ МОДЕЛЕЙ ИС
│
├── По формализованности
│   ├── неформальные
│   └── формальные
│
├── По зависимости от реализации
│   ├── логические
│   └── физические
│
├── По фактору времени
│   ├── статические
│   └── динамические
│
├── По содержанию
│   ├── функциональные
│   ├── информационные
│   ├── поведенческие
│   ├── компонентные
│   ├── организационные
│   └── смешанные
│
└── По состоянию
    ├── AS-IS      — как есть
    ├── SHOULD-BE  — как должно быть по нормативам
    └── TO-BE      — как будет после внедрения ИС
```

Очень важно: **это не одна иерархия типов**. Одна модель может быть
одновременно, например, структурированной + логической + статической, потому что
мы ее классифицируем **по разным признакам**.
