# Жизненный цикл информационной системы

*Жизненный цикл информационной системы* (ЖЦ ИС) - это совокупность взаимосвязанных
процессов (стадий, этапов), начинающихся с момента принятия решения о создании
ИС и заканчивающихся в момент полного изъятия ее из эксплуатации.

`Ключевая мысль: жизненный цикл это не только разработка.`

```plaintext
                 ЖИЗНЕННЫЙ ЦИКЛ ИС

Решили создать
      │
      ▼
Требования
      │
      ▼
Проектирование
      │
      ▼
Реализация
      │
      ▼
Тестирование
      │
      ▼
Внедрение
      │
      ▼
Эксплуатация
      │
      ▼
Сопровождение
      │
      ▼
Вывод из эксплуатации
```

То есть когда программист написал последний endpoint - жизненный цикл не
закончился. Система может потом десять лет эксплуатироваться, обновляться,
исправляться и сопровождаться. И все это остается частью ее ЖЦ.

Например:

```plaintext
2026
Решили разработать LMS
        ↓
Собрали требования
        ↓
Спроектировали
        ↓
Написали
        ↓
Протестировали
        ↓
Внедрили

2027–2032
Эксплуатация + сопровождение
        ↓
2033
Систему заменили новой
        ↓
Старую полностью вывели
из эксплуатации
```

Только в 2033 году в этом примере закончился жизненный цикл этой ИС.

## Процесс, стадия и этап

Процесс, стадия и этап - это некоторая декомпозиция работ в ЖЦ ИС.

```plaintext
Жизненный цикл
      │
      ├── Стадия
      │      │
      │      ├── Этап
      │      └── Этап
      │
      ├── Стадия
      │      │
      │      ├── Этап
      │      └── Этап
      │
      └── ...
```

То есть ЖЦ - **это весь путь системы**, а внутри него находятся конкретные
процессы/стадии/этапы работ.

Некоторые этапы разрешено выполнять параллельно или даже начинать до полного
завершения предыдущих стадий.

## Процессы жизненного цикла

На самом верхнем уровне процессы разделены на:

```plaintext
             ПРОЦЕССЫ ЖИЗНЕННОГО ЦИКЛА
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
        Общесистемные            Специальные
      (системы любого типа)   (программные средства,
                               ≈ информационные системы)
```

### Общесистемные

Общесистемные процессы - это такое процессы, которые могут понадобиться не
только при создании ПО.

Например:

- менеджмент проекта;
- менеджмент рисков;
- менеджмент качества;
- менеджмент информации;
- планирование;
- измерения;
- приобретение;
- поставка.

`Логично: рисками, качеством, ресурсами и проектами управляют не только программисты.`

### Специальные

Специальные процессы непосредственно относятся к программным средствам.

Например:

```plaintext
анализ требований ПО
        ↓
проектирование архитектуры ПО
        ↓
детальное проектирование
        ↓
конструирование
        ↓
интеграция
        ↓
квалификационное тестирование
```

Кроме реализации ПО существуют процессы его поддержки:

- документация;
- конфигурация;
- обеспечение качества;
- верификация;
- валидация;
- ревизия;
- аудит;
- решение проблем.

## Классический ЖЦ

Классический ЖЦ выглядит следующим образом:

```plaintext
Формирование требований
          ↓
Анализ требований
          ↓
Проектирование
          ↓
Кодирование (реализация)
          ↓
Тестирование
          ↓
Внедрение
          ↓
Эксплуатация
```

### Этап формирования требований

`Сначала нужно понять: что вообще должна делать будущая система?`

Например, заказчик хочет LMS. Мы выясняем:

```plaintext
Студент должен:
├── видеть свои курсы;
├── проходить материалы;
├── проходить тестирование;
└── видеть результаты.

Администратор должен:
├── создавать пользователей;
├── зачислять их на курсы;
└── просматривать статистику.

Система должна:
├── хранить результаты обучения;
├── разграничивать права доступа;
└── ...
```

То есть на этой стадии определяем требования к будущей системе.

Требования бывают **функциональные** и **нефункциональные**.

```plaintext
Требования
│
├── Функциональные
│   └── ЧТО система должна делать
│
└── Нефункциональные
    └── КАКИМИ характеристиками она должна обладать
```

### Этап анализа требований

**Формирование требований** -> выясняем, что хочет заказчик.
**Анализ требований** -> разбираемся с этими требованиями перед проектированием.

Например, заказчик говорит, что студент должен проходить тест. При анализе
возникает куча вопросов:

- сколько попыток разрешено?
- есть ли ограничение времени?
- можно ли вернуться к предыдущему вопросу?
- как определяется результат?
- что происходит при разрыве соединения?
- кто может смотреть результаты?

То есть исходное "Студент проходит тест" становится гораздо более определенным
набором требований.

### Этап проектирования

Этап проектирования отвечает на вопрос: **как должна быть устроена система, чтобы
эти требования реализовать?**

Этому соответствуют:

- проектирование архитектуры системы;
- проектирование архитектуры программного средства;
- детальное проектирование программного средства.

На этом этапе появляются проектные решения, например:

```plaintext
             Web Client
                  │
                  │ HTTP
                  ▼
               Server
              /      \
             ▼        ▼
       PostgreSQL   Storage
```

Определяются информационные потоки и проектируется структура данных:

```plaintext
Student
   │
   │
Enrollment
   │
   ▼
Course
```

Определяются компоненты системы и связи между ними.

Хорошая граница:

```plaintext
ТРЕБОВАНИЯ

"Студент должен иметь возможность
проходить назначенные ему курсы."

                ↓

ПРОЕКТИРОВАНИЕ

Как представить Course?
Как связать Student и Course?
Какие компоненты системы нужны?
Как они взаимодействуют?
Как хранить данные?
```

То есть **требование говорит, что нам нужно получить. Проектное решение - как мы
собираемся это реализовать.**

### Кодирование / реализация

Этот этап отвечает за реализацию ранее принятого проектного решения.

```plaintext
Проектная модель
      ↓
Исходный код
      ↓
Работающее ПО
```

Например:

```go
type Enrollment struct {
    StudentID int
    CourseID  int
}
```

### Тестирование

После реализации необходимо проверить систему.

### Внедрение

Система разработана и протестирована, но это еще не означает "Ну все,
пользователи работают". Систему необходимо **внедрить**.

Этой стадии соответствуют:

```plaintext
Инсталляция (установка) ПС
           ↓
Поддержка приёмки ПС
```

Работы на стадии внедрения удобно представить следующим образом:

```plaintext
Разработанная ИС
      │
      ▼
Предварительные испытания
      │
      ▼
Опытная эксплуатация
      │
      ▼
Приёмочные испытания
      │
      ▼
Постоянная эксплуатация
```

#### Предварительные испытания

**Предварительные испытания** проводят, чтобы определить работоспособность ИС и
решить, можно ли принять ее в опытную эксплуатацию.

```plaintext
Практический пример

Допустим, команда делает новый модуль для ЛК ДВГУПС. На стадии тестирования
разработчики и тестировщики проверили модуль и знают его текущее состояние. При
этом вполне может оказаться, что продукт **не идеален**: где-то остались
ограничения, недоделанные вещи, известные дефекты и т.д.

Но наличие багов/заглушек не обязательно автоматически означает, что нельзя
допускать систему в опытную эксплуатацию. Конкретное решение зависит от
установленных требований и порядка испытаний.
```

#### Опытная эксплуатация

Систему допустили к использованию, но пока не к окончательной постоянной
эксплуатации. Теперь ее используют, чтобы определить, как она себя показывает в
фактической работе.

Выделяют следующие цели:

```plaintext
Опытная эксплуатация
│
├── определить фактические количественные
│   и качественные характеристики ИС
│
├── определить готовность персонала
│   к работе с системой
│
├── определить фактическую эффективность
│   работы ИС
│
└── при необходимости
    скорректировать документацию
```

До этого этапа были проектные представления, что система должна работать "вот так".
А теперь она попадает в эксплуатационные условия с реальными данными, и мы
смотрим "а как система работает на самом деле?".

```plaintext
Например, система технически исправна, но выясняется, что персонал не готов с
ней работать или документация недостаточно понятна. Это как раз те вещи, которые
позволяет обнаружить опытная эксплуатация.
```

#### Приемочные испытания

На данном этапе определяется, можно ли окончательно принять систему в постоянную
эксплуатацию.

Здесь появляется важная связь с ТЗ. В начале проекта требования формализуются в
соответствующей проектной документации, а при приемке проверяется:

```plaintext
Техническое задание
«Что требовалось создать»
        │
        │ сравниваем
        ▼
Фактически созданная ИС
«Что получилось»
```

### Эксплуатация

Теперь системой **реально пользуются**.

На этом этапе функционирование программного средства объединяется с его сопровождением.

```plaintext
Пользователи
     │
     ▼
работают с системой
       +
систему исправляют,
обновляют и сопровождают
```

#### Сопровождение

Система уже внедрена и эксплуатируется, но работа над ней не заканчивается.

```plaintext
Постоянная эксплуатация
        │
        ├── система используется
        │
        └── система сопровождается
```

##### Гарантийные обязательства

**Гарантийные обязательства** выполняются бесплатно согласно договору. К ним относятся:

```plaintext
Гарантийные обязательства
│
├── устранение выявленных недостатков и ошибок
│
├── внесение необходимых изменений
│   в программы и документацию
│
├── внесение изменений
│   в технологический процесс
│
└── консультации пользователей
```

Это не означает, что "любой баг после релиза разработчик обязан бесплатно
исправить". Все завязано на гарантийные обязательства по договору.

##### Послегарантийные обязательства

После окончания гарантийных обязательств сопровождение может продолжаться, но
уже за отдельную плату.

Сюда попадают:

```plaintext
Послегарантийные обязательства
│
├── анализ функционирования системы
│
├── выявление отклонений фактических
│   эксплуатационных характеристик
│   от проектных и поиск их причин
│
├── устранение недостатков и обеспечение
│   стабильности характеристик ИС
│
├── изменение документации
│
├── дополнительное обучение пользователей
│
└── передача очередных версий
```

Здесь речь уже не только про "нашли баг -> исправили". Сопровождение может
включать анализ того, **как система ведет себя при эксплуатации, актуализацию
документации, дополнительное обучение пользователей, передачу новых версий и
т.д.".

### Прекращение применения

```plaintext
Жизненный цикл ИС

Решение о создании
       │
       ▼
     ...
       │
       ▼
 Эксплуатация
       │
       ▼
Прекращение применения
       │
       ▼
Полное изъятие
из эксплуатации

       КОНЕЦ ЖЦ
```

ЖЦ действительно охватывает всю жизнь системы, а не только разработку.

### Особенности жизненного цикла ИС

Структура жизненного цикла не является абсолютно жесткой.

Допускается:

- исключать отдельные этапы работ;
- начинать отдельные этапы до завершения предшествующих стадий;
- выполнять отдельные этапы параллельно;
- добавлять дополнительные этапы работ.

### Роли участников проекта

Общую картину можно представить так:

```plaintext
Заказчик / предметная область
            │
            ▼
     Эксперт-технолог
            │
            ▼
     Системный аналитик
       / архитектор
            │
            ▼
      Проектировщик
            │
            ▼
       Программист
            │
            ▼
       Тестировщик
            │
            ▼
  Инженер по внедрению
            │
            ▼
        Пользователь

Менеджер проекта → управляет всем проектом
Технический писатель → готовит документацию
```

#### Руководитель (менеджер) проекта

**Руководитель (менеджер) проекта** отвечает прежде всего за организационную сторону:

- ищет потенциальных заказчиков;
- заключает договор;
- планирует сроки и ресурсы;
- управляет и контролирует ход проекта;
- взаимодействует с заказчиком.

То есть он не отвечает на вопрос "какую архитектуру backend нам выбрать?". Его
уровень "что делаем, для кого, какими ресурсами, в какие сроки и как идет
проект?".

```plaintext
Менеджер проекта
│
├── заказчик
├── сроки
├── ресурсы
└── контроль проекта
```

#### Эксперт-технолог

**Эксперт-технолог**:

- делает постановку задачи;
- совместно с системным аналитиком определяет основные функциональные и нефункциональные требования;
- определяет технологию использования системы;
- консультирует разработчиков;
- участвует в приёмке.

Проще говоря, это человек, который хорошо понимает **предметную область и то, как
система должна использоваться в ней.**

Например, мы разрабатываем систему для железной дороги. Разработчик может прекрасно
знать Go / PostgreSQL / Svelte, но не знать железнодорожных технологических процессов.

```plaintext
Эксперт-технолог

Предметная область
       │
       ▼
«Вот как реально
выполняется эта работа»
       │
       ▼
Разработчики
```

Он помогает команде понять, что **именно необходимо автоматизировать** и **как это должно
работать с точки зрения предметной области.**

#### Системный аналитик (архитектор, главный конструктор)

**Системный аналитик**:

- определяет функциональные и нефункциональные требования;
- анализирует требования;
- ищет пути их реализации на уровне концепции системы;
- задаёт архитектуру системы;
- отвечает за соответствие моделей выбранной архитектуре.

```plaintext
Требования
    │
    ▼
Системный анализ
    │
    ▼
Как эти требования
могут быть реализованы?
    │
    ▼
Архитектура системы
```

Квалифицированный аналитик должен быть специалистом **и в разработке ПО, и в
предметной области.**

Легко спутать роль системного аналитика и эксперта-технолога. Поэтому разделим
их деятельность следующим образом:

```plaintext
ЭКСПЕРТ-ТЕХНОЛОГ

сильнее со стороны
предметной области

«Как устроена деятельность,
которую автоматизируем?»


СИСТЕМНЫЙ АНАЛИТИК

связывает требования
с будущей системой

«Какую систему нужно
спроектировать для этого?»
```

При этом они работают **вместе** над требованиями.

#### Проектировщик

**Проектировщик** разрабатывает модели системы на основе архитектуры.

```plaintext
Системный аналитик / архитектор
              │
              │ задаёт архитектуру
              ▼
        Проектировщик
              │
              │ разрабатывает
              ▼
        Модели системы
```

#### Программист

**Программист** - реализует модели в виде программного обеспечения.

```plaintext
Требования
    ↓
Анализ
    ↓
Архитектура
    ↓
Модели
    ↓
ПРОГРАММИСТ
    ↓
Программное обеспечение
```

#### Тестировщик

**Тестировщик** - разрабатывает тесты и тестирует модели системы и разработанное
ПО.

#### Технический редактор / писатель

**Технический редактор (писатель)** занимается пользовательской документацией.

В комплект документации могут входить:

- технологические инструкции;
- руководство пользователя;
- руководство администратора;
- руководство по БД;
- и другие.

То есть разработать систему недостаточно - кто-то должен еще объяснить, как с
ней работать.

#### Инженер по внедрению

**Инженер по внедрению** занимается внедрением системы на объекте автоматизации.
В его функции могут входить:

```plaintext
установка
    ↓
настройка
    ↓
обучение пользователей
```

То есть разработчики сделали систему, а инженер по внедрению помогает привести
ее в рабочее состояние **непосредственно там, где она будет эксплуатироваться.**

#### Пользователь

**Пользователь** эксплуатирует систему в штатном режиме. Желательно вовлекать
пользователя в **формирование требований.**
